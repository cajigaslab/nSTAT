# Deep-Dive Verification Plan — All Examples Run + Accurate Results + Visual Inspection

> **Goal:** end-to-end verification that *every* user-facing example in nSTAT (38 helpfiles + 5 paper examples + 3 new tutorials) (a) runs to completion, (b) produces numerically accurate results given known inputs, and (c) has visually-inspectable output figures that match the prose claims and (where applicable) the published 2012 paper.

> **Date:** 2026-05-20
> **Master HEAD:** `4303305` (post-PR #39, all Phase 0-4 work merged)
> **Effort estimate:** 1-3 days of focused work depending on phase scope.

---

## Strategic counterargument first

**Don't do this if you don't have a downstream consumer.** Deep verification produces a static artifact (a verification report at a single point in time). The toolbox already works — every paper example runs end-to-end with zero deprecation warnings; the unit-test suite is green. If no one is about to use the toolbox for active research, deep verification is making the bed nobody sleeps in.

The strongest argument for doing it anyway: **scientific publication credibility.** If you intend to cite nSTAT in a paper (or distribute it to clinical collaborators), having a published verification report saying "all 46 user-facing scripts produce X output on R2025b on 2026-05-20" is the right citation hook. That use case justifies the effort. Pure code-quality concern does not.

Confidence: high on the strategic question. **Proceed only if there's a citation/distribution motive.** If you say go, the plan below is the right shape.

---

## Scope

### In scope

- **5 paper examples** in `examples/paper/example0[1-5]_*.m`
- **38 helpfiles** in `helpfiles/*.m` — tutorials and class-specific demos
- **3 new tutorials** added in PR #36: `HelloNstat`, `InternalValidation`, `WhenToUseWhich`
- **Output figures** generated by each script (PNG, into `docs/figures/<script_id>/`)
- **Numerical accuracy** of key outputs (KS statistics, fitted coefficients, log-likelihoods) against analytic expectations or published values
- **Visual inspection** of every generated figure for correctness and consistency

### Out of scope

- Code refactoring (any required fixes are tracked as separate PRs).
- Performance optimization (DecodingExampleWithHist takes 213s — noted, not fixed).
- Python port verification (separate repo: `cajigaslab/nSTAT-python`).
- The 14-model curriculum KS-validation zoo (already covered by `tests/integration/testKsAgainstReferenceZoo`).
- The `Analysis.m:609` empty-`b` defect (latent; separate PR).

### Acceptance criteria

**Runtime acceptance:** every script in scope exits with status 0 and emits zero `nSTAT:deprecated:*` warnings.

**Numerical acceptance** (per category):
- **Paper examples:** key reported numerics (KS statistic, AIC, BIC, fitted coefficients) must match the published 2012 paper values within the documented `Seed=0` reproducibility envelope (≤ 5% deviation on log-likelihood ratios; coefficient signs and order of magnitude correct).
- **Tutorial examples** (HelloNstat etc.): fitted intercept must recover `log(λΔ)` of the simulated rate within Bernoulli sampling SE.
- **Helpfile demonstrations:** must exercise the documented class API without silent corruption (no NaN propagation, no dimension mismatch warnings).
- **KS plots:** the oracle / correct-CIF cases must produce a KS curve that stays within the 95% confidence band; misspecified-model demos must visibly exceed the band.

**Visual acceptance:**
- Every figure has a title, axis labels, and (where applicable) a legend.
- Figures match the prose description in the script's docstring or the paper section it claims to reproduce.
- No cropped axes, no overlapping text, no missing data series.

## Phase structure

The plan is 5 phases. Each ships as a distinct PR so partial progress is reviewable.

### Phase V0 — Inventory + harness (~2-3 hr)

Build the verification scaffold that subsequent phases run against. **No verification yet.**

#### V0.1 Catalog every script

Create `docs/verification/script_inventory.md` listing every in-scope script with: file path, category (paper/tutorial/helpfile-tutorial/helpfile-demo), data dependency (synthetic / figshare / placecell-results), and expected output category (figures-only / numerical-only / both).

**Concrete output:** a markdown table with ~46 rows. Generate it programmatically (`grep -lE` patterns over `helpfiles/`) so future scripts auto-register without manual edits.

#### V0.2 Verification harness script

Create `tools/verify_all_examples.m` — a single MATLAB driver that:
1. Reads the inventory.
2. For each script:
 - Runs it in a captured environment (`evalc` for stdout, `lastwarn` for warnings, `tic`/`toc` for timing).
 - Captures any figures created via a `findobj`-based snapshot, saves to `docs/figures/<script_id>/`.
 - Extracts numerical outputs (any `fprintf`'d numbers + assigned base-workspace variables matching a known schema).
 - Records pass / fail / runtime / warnings / output-artifact paths.
3. Emits a JSON report at `docs/verification/run_report_<timestamp>.json`.
4. Emits a markdown summary at `docs/verification/REPORT.md` (gets overwritten each run).

**Test the harness on a known-clean script** (`HelloNstat.m`) before scaling. Acceptance: harness correctly captures the 3 figures and the 4 reported numerics (logLL, AIC, BIC, fitted intercept).

#### V0.3 Manifest update

Extend `docs/figures/manifest.json` to include helpfile + tutorial entries with the same schema as paper examples (`example_id`, `title`, `source_script`, `description`, `figure_files`, `paper_mapping` where applicable).

**PR for Phase V0:** `verify/phase-v0-harness` — 3 commits (inventory, harness, manifest extension). 100% scaffolding, zero verification claims yet.

### Phase V1 — Runtime verification (~3-4 hr)

Goal: confirm every in-scope script **runs to completion** under R2025b on the current master.

#### V1.1 Run paper examples (already largely done)

The end-to-end verification subagent already confirmed all 5 paper examples pass with zero deprecation warnings. Re-run via the new harness to capture artifacts + timing in the JSON report.

**Expected:** 5/5 pass. Total runtime ~152s.

#### V1.2 Run new tutorials

`HelloNstat`, `InternalValidation`, `WhenToUseWhich` (note: WhenToUseWhich is documentation-only; just verify it `publish()`-renders without errors).

**Expected:** 3/3 pass. Total runtime ~5s.

#### V1.3 Run helpfile examples — Tier A (the migrated 4)

`DecodingExample.m`, `DecodingExampleWithHist.m`, `StimulusDecode2D.m`, `HybridFilterExample.m` — these were touched by the Phase 3.5b migration. Already verified clean post-PR #39.

**Expected:** 4/4 pass. Total runtime ~232s (DecodingExampleWithHist dominates).

#### V1.4 Run helpfile examples — Tier B (the other 34)

Run the remaining 34 helpfiles. Many are small class-specific demos (`SignalObjExamples.m`, `nSpikeTrainExamples.m`, etc.); a few are larger paper-aligned tutorials (`mEPSCAnalysis.m`, `HippocampalPlaceCellExample.m`, `nSTATPaperExamples.m`).

This is the **largest unknown** in the plan — these scripts haven't been routinely run since at least the Feb 2026 audit. Likely some fraction will fail on R2025b due to:
- Removed APIs (`spectrum.periodogram` style — Phase 3.7 fixed two but there may be more)
- Path drift (referencing `paperData/...` that doesn't exist)
- Variable-name shadowing (`time`, `data` as both variables and methods)
- Missing dependencies (some helpfiles use `nSTATPaperExamples.mlx`-only setup)

**Expected:** unknown failure rate. Plan accommodates 25-75% failure on first pass.

#### V1.5 Triage failures

For each failed script, categorize:
- **A. Stale `.mlx`** (like PR #39's findings) — delete the `.mlx` if it shadows a working `.m`.
- **B. Removed API** — file a fix PR analogous to Phase 3.7 SignalObj modernization.
- **C. Missing data** — document the data dependency in the script's docstring; if data is figshare, note the `nSTAT_Install('DownloadExampleData', true)` requirement.
- **D. Script-level bug** (broken syntax, undefined variable) — file a fix PR.
- **E. Out-of-scope** (e.g., requires a deprecated CSV format) — mark as quarantine: move to `helpfiles/legacy/`.

**PR for Phase V1:** `verify/phase-v1-runtime` — depends on V0. Outputs the run-report JSON + categorized failure list. Does NOT fix anything; just reports.

### Phase V2 — Numerical accuracy verification (~4-6 hr)

For each script that passes V1, verify the **numerical output matches expectation**.

#### V2.1 Paper examples vs published values

For each of the 5 paper examples, the 2012 paper (Cajigas, Malik, Brown 2012) reports specific results:
- Example 1 (mEPSC): KS statistic for constant-rate model on Mg²⁺-free data.
- Example 2 (whisker): lag estimate; coefficient values for stim + history models; KS for each.
- Example 3 (PSTH + SSGLM): trial-drift variance estimates.
- Example 4 (place cells): receptive-field coefficient comparison (Gaussian vs Zernike basis); KS for each.
- Example 5 (decoding): MSE for PPAF vs PPHF on the simulated reach data.

Extract these values from the published paper (DOI `10.1016/j.jneumeth.2012.08.009`; PMC `PMC3491120` for open access). For each, compare the script's current output to the paper's published value.

**Acceptance:** within 5% on continuous values; exact match on pass/fail KS verdicts; sign and order-of-magnitude match on coefficients.

**Output:** `docs/verification/paper_accuracy_table.md` — a side-by-side table (paper value, current value, deviation, status).

#### V2.2 Tutorial examples — self-consistency

For each tutorial (HelloNstat, InternalValidation), the script generates its own ground truth (known rate → simulated spikes → fit) and the prose makes specific claims. Verify:
- HelloNstat: fitted intercept within ±2 SE of `log(λΔ)`; KS plot inside band.
- InternalValidation: oracle PASSES, misspecified FAILS, with KS stat ratio matching prose ("FAIL by ~2x the band").

**Acceptance:** quantitative claims in the prose match runtime values.

#### V2.3 Helpfile demos — API-correctness check

For each demonstrative helpfile (e.g., `SignalObjExamples.m`, `nSpikeTrainExamples.m`):
- Run with `rng(0, 'twister')`.
- Capture stdout numerics.
- Verify the script's **stated purpose** is exercised (e.g., `SignalObjExamples` actually constructs and plots `SignalObj`s; `nSpikeTrainExamples` actually fits and plots burst statistics).
- No NaN propagation in any numeric output.
- No silent dimension errors.

**Acceptance:** subjective — the script visibly demonstrates the class. Hard fails (NaN-only outputs, dimension errors masked as warnings) are reported.

**PR for Phase V2:** `verify/phase-v2-accuracy` — outputs the paper-accuracy table + the per-helpfile API-correctness table. Does NOT fix discrepancies; reports them.

### Phase V3 — Visual inspection (~6-8 hr; can be partly automated)

For each script that produces figures, render and inspect every figure.

#### V3.1 Render gallery

Use the V0.2 harness to generate every figure into `docs/figures/<script_id>/`. Update `manifest.json` to include the new helpfile-figure entries.

#### V3.2 Build visual-inspection markdown

Create `docs/verification/figure_gallery.md` — one section per script with:
- Script name + one-line purpose
- All figures inlined (markdown `![](path)` syntax)
- The prose claim each figure is illustrating
- An "inspection checklist": axes labels present? legend present? data series complete? title accurate?

This is the artifact a human reviewer (you) inspects. Each figure gets a ✓ or ⚠️ or ❌ tick.

#### V3.3 Automated visual sanity checks

For each PNG, automated checks:
- File is non-empty (>1 KB).
- Image is not entirely black or entirely white (using simple ImageMagick or Python PIL check).
- Image dimensions are sensible (>200×200 px).

These don't catch substantive issues (wrong data, mislabeled axes) but catch render failures.

#### V3.4 Manual visual review

This is the irreducible human step. Open `docs/verification/figure_gallery.md` in a Markdown viewer that renders inlined PNGs (VS Code, Obsidian, GitHub). For each figure:
- Does the title match what the script is doing?
- Are axes correctly labeled with units?
- For KS plots: is the diagonal visible? Is the 95% band visible? Does the curve lie where prose says?
- For PSTH plots: is the rate axis in Hz? Are bins sensibly sized?
- For receptive-field plots: are the units (position vs rate) clear?

Flag each figure as PASS or REVIEW with a one-line concern note.

**PR for Phase V3:** `verify/phase-v3-visual` — the gallery markdown + manifest update + automated-check PNG metadata. Manual inspection happens in a PR-comment thread.

### Phase V4 — Reporting + remediation plan (~2-3 hr)

Synthesize results from V1-V3 into a single verification report. Identify any items requiring follow-up fixes; group them into a remediation plan.

#### V4.1 Master verification report

`docs/verification/REPORT.md` — single document with:
- Summary table (script → status across V1/V2/V3)
- Per-failure detail with proposed fix or quarantine recommendation
- Numerical-accuracy deviation list
- Visual-inspection concern list
- Sign-off section: "On 2026-05-DD, N/M scripts verified. Reviewer: <name>"

#### V4.2 Remediation backlog

For every issue surfaced in V1-V3, create a tracked item:
- Title (e.g., "Fix removed spectral API in `nSpikeTrainExamples.m`")
- Affected files
- Proposed fix shape
- Acceptance criteria for the fix

Save as `docs/verification/remediation_backlog.md`. This becomes the input to subsequent PRs.

#### V4.3 Citation-ready snippet

Generate the canonical citation paragraph for inclusion in a paper:

> The nSTAT toolbox (commit `<sha>`, master HEAD 2026-05-DD) was verified end-to-end on MATLAB R2025b. All N of M user-facing scripts ran to completion with zero deprecation warnings. Paper-example numerical outputs match Cajigas et al. 2012 within 5%; tutorial-example outputs match analytic expectations within Bernoulli sampling SE. The verification report is at `docs/verification/REPORT.md` and figure gallery at `docs/verification/figure_gallery.md`.

**PR for Phase V4:** `verify/phase-v4-report` — the synthesized report + backlog. No code changes; ships the verification artifact.

## Dependencies + sequencing

- **V0 → V1 → V2 → V3 → V4** is strict sequential. Each phase depends on the previous artifact.
- V2 can partially parallelize with V3 (numerical accuracy and visual inspection are independent for any script that passes V1).
- The harness from V0 is reusable for future verification runs — write it well; this is the load-bearing infrastructure.

---

## What this plan deliberately does NOT do

- **Does not fix anything.** Findings are reported, not patched. Fixes go in separate PRs after this plan delivers the remediation backlog. Keeping verification and remediation separate avoids the trap of "I verified what I just changed."
- **Does not regenerate paper figures.** The figures already exist in `docs/figures/example0[1-5]/`. We compare those to the paper, not regenerate them.
- **Does not modify the harness once committed in V0.** If V1 surfaces a script that the harness can't handle (e.g., a script that calls `clear all` and confuses the wrapper), document the limitation; don't patch the harness mid-flight.
- **Does not require Python.** The verification is pure-MATLAB for the math + bash for orchestration.

## Recommendation for execution

**Two paths:**

1. **Full plan, sequential** — execute V0 → V1 → V2 → V3 → V4 across 2-3 focused days. Output: a citation-ready verification report.

2. **MVP-first** — execute V0 + V1 only (~6 hours, 1 day). Output: list of broken scripts + categorized failure reasons, but no accuracy or visual inspection.

If the motivation is citation/distribution, do path 1. If the motivation is "I want to know what's broken right now without committing to a multi-day effort," do path 2.

The third path is to **not do this at all** (per the strategic counterargument at the top). The toolbox works on paper examples; the unit tests pass; the recent verification subagent confirmed 11/11 scripts. Deep verification is appropriate only if you have a downstream consumer that needs the report.
